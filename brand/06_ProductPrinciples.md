# 产品设计原则

本文件定义未来产品评审使用的 proposed 原则，不要求在本 Sprint 修改现有 UI。

## 1. 记录是为了理解，不是为了监控

- **原则定义：** 记录应帮助用户发现规律，不把生活变成持续监视。
- **用户价值：** 用户知道为什么记录，并可控制记录范围。
- **正面示例：** 用睡眠与训练趋势解释恢复变化。
- **反面示例：** 要求全天候采集与当前目标无关的数据。
- **对 UI 的影响：** 说明记录用途，允许跳过和删除。
- **对 Agent 的影响：** 只使用与问题相关的数据。
- **对数据架构的影响：** 支持最小化采集、来源标记和删除。
- **验收问题：** 这个记录能帮助用户理解什么？

## 2. 数据是成长轨迹，不是成绩单

- **原则定义：** 数据用于观察变化，不用于评判人的价值。
- **用户价值：** 波动和未完成也能成为可用信息。
- **正面示例：** 展示月度趋势并标注现实背景。
- **反面示例：** 用单一总分给人生贴上好坏标签。
- **对 UI 的影响：** 趋势、背景与复盘优先于排名。
- **对 Agent 的影响：** 不用羞耻或比较解释数据。
- **对数据架构的影响：** 保留时间、上下文与用户备注。
- **验收问题：** 这个呈现是在帮助理解，还是在打分？

## 3. AI 建议必须解释原因

- **原则定义：** 每项建议都应说明依据、限制和适用条件。
- **用户价值：** 用户可以判断建议是否适合自己。
- **正面示例：** 因睡眠不足和疲劳升高而建议降强度。
- **反面示例：** 只输出“今天休息”而不解释。
- **对 UI 的影响：** 建议旁可查看依据与风险。
- **对 Agent 的影响：** 输出 findings、recommendations 和 warningFlags。
- **对数据架构的影响：** 保存输入版本、规则版本与理由。
- **验收问题：** 用户能否理解这项建议为什么出现？

## 4. 最终决定权属于用户

- **原则定义：** 系统提供支持，不替用户做最终选择。
- **用户价值：** 保留目标、行动与风险接受度的自主权。
- **正面示例：** 建议可修改、拒绝并记录原因。
- **反面示例：** 自动更改目标且不允许撤销。
- **对 UI 的影响：** 明确确认、编辑和拒绝入口。
- **对 Agent 的影响：** 使用建议性语言并说明权衡。
- **对数据架构的影响：** 区分系统建议与用户最终决定。
- **验收问题：** 用户能否安全地作出不同选择？

## 5. 优先展示可执行行动，而不是堆积指标

- **原则定义：** 先给与当前目标相关的下一步，再提供细节。
- **用户价值：** 降低信息负担，知道今天可以做什么。
- **正面示例：** 首先显示“低强度 30 分钟或休息”及原因。
- **反面示例：** 首屏堆满无法解释的指标。
- **对 UI 的影响：** 行动与关键风险优先，详情按需展开。
- **对 Agent 的影响：** 建议具体、有限且可执行。
- **对数据架构的影响：** 区分行动、依据与原始指标。
- **验收问题：** 用户看完是否知道下一步？

## 6. 同时关注当下状态和长期变化

- **原则定义：** 决策同时参考今天的感受与一段时间的趋势。
- **用户价值：** 避免被单日波动或长期平均误导。
- **正面示例：** 结合昨晚睡眠和四周训练负荷调整计划。
- **反面示例：** 只凭今天心情或历史平均给建议。
- **对 UI 的影响：** 同屏区分今日信号与长期趋势。
- **对 Agent 的影响：** 标明短期、长期证据及冲突。
- **对数据架构的影响：** 支持时间序列、窗口和来源。
- **验收问题：** 决策是否兼顾当前与趋势？

## 7. 不用焦虑、羞耻或攀比驱动用户

- **原则定义：** 行动来自理解和选择，不来自情绪操控。
- **用户价值：** 建立可持续、尊重自我的成长关系。
- **正面示例：** 把未完成计划转化为调整依据。
- **反面示例：** 用连续打卡中断惩罚或同龄人排名施压。
- **对 UI 的影响：** 避免红色羞辱提示和强迫性排行榜。
- **对 Agent 的影响：** 不责备、不比较、不许诺完美结果。
- **对数据架构的影响：** 不为操控性增长指标采集额外数据。
- **验收问题：** 这个功能是否通过让用户感到不足来驱动使用？

## 8. 健康建议不能冒充医疗诊断

- **原则定义：** 产品提供日常决策支持，不越过医疗边界。
- **用户价值：** 获得清楚风险提示，同时避免虚假诊断。
- **正面示例：** 高风险疼痛时建议暂停并寻求专业评估。
- **反面示例：** 根据截图宣布疾病或治疗方案。
- **对 UI 的影响：** 风险、非诊断说明和求助条件清晰可见。
- **对 Agent 的影响：** 不确定性与转介条件必须输出。
- **对数据架构的影响：** 风险标记不能伪装成诊断字段。
- **验收问题：** 用户会不会把这项输出误解为医疗结论？

## 9. 所有核心资产必须可导出和迁移

- **原则定义：** 数据、文档、Schema、Prompt 和规则不被单一平台锁定。
- **用户价值：** 用户和项目可以备份、恢复与更换工具。
- **正面示例：** 提供结构化导出、文件索引和校验值。
- **反面示例：** 关键历史只能在不可导出的专有界面查看。
- **对 UI 的影响：** 数据管理中提供清楚的导出与恢复入口。
- **对 Agent 的影响：** 规则和输出使用带版本的开放结构。
- **对数据架构的影响：** 使用稳定标识、Schema 和迁移清单。
- **验收问题：** 离开当前平台后，核心资产能否被验证并继续使用？

## 10. 任何 AI 服务商都应当可以被替换

- **原则定义：** AI 是适配层能力，品牌和业务规则不依附单一厂商。
- **用户价值：** 获得更稳定的长期服务与提供商选择权。
- **正面示例：** 规则版、本地模型和云模型共享分析契约。
- **反面示例：** 业务真相只存在某个供应商的私有 Prompt 中。
- **对 UI 的影响：** 不把厂商品牌当作产品身份核心。
- **对 Agent 的影响：** 输入输出结构与提供商实现分离。
- **对数据架构的影响：** 保存提供商、模型与版本元数据，不改变核心数据。
- **验收问题：** 更换 AI 提供商是否会迫使我们重写核心资产？
